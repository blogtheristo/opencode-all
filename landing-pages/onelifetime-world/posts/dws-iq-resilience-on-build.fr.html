DWS IQ 6 — Continuité dans le build

20.08.2026 · Risto Päärni · Espoo, Finlande

Note de terrain approuvée HIC · Cette page a été rédigée avec l'aide de l'IA et examinée par un réviseur humain nommé avant publication (human-in-the-loop, règlement européen sur l'IA, article 14).

Le cœur du sujet

Si tout un flux de développement s'arrête dès qu'un fournisseur d'IA change de direction, ce n'est pas une pile résiliente. C'est une dépendance.

Les modèles changent chaque mois. Les prix changent. Les politiques changent. Le produit doit continuer d'être construit à travers tout cela.

Chez Lifetime Oy, nous avons fait de la continuité un objectif de conception.

Trois décisions portent cela :

  • Les modèles open source locaux sont la norme pour le développement quotidien. Les fondations restent dans le bâtiment.
  • Les modèles frontier entrent sur invitation. Lorsqu'une tâche est trop difficile pour le modèle local, le modèle frontier fait le gros du travail et rend le travail.
  • Les standards voyagent avec le travail, pas avec le fournisseur. Notre Truth Standard, l'ontologie DWS et les dictionnaires de domaine protègent la traçabilité et tiennent les affirmations non étayées et le gonflement de l'IA hors de la base de code, quel que soit le modèle qui a écrit le code.

Je ne prétends pas que cela nous rend insensibles aux fournisseurs. La continuité est l'objectif, et vous ne savez à quel point vous en êtes proche qu'en testant honnêtement une question :

Si votre principal fournisseur d'IA changeait ses prix ou ses politiques demain, quelle part de votre flux de développement continuerait de fonctionner ?

L'histoire

Juin 2026 a été mon meilleur mois de construction avec Claude. Depuis octobre 2025, l'apprentissage du codage avec l'IA et la construction du modèle de production Firehorse ont apporté de la vitesse et créé 116 produits en un an — sans oublier les premiers mois avec Cursor.AI et Visual Studio Code, lorsque le code était encore préparé par un humain dans la boucle. Dans l'ensemble, la croissance de Claude Code en tant qu'outil connecté m'a rendu 10x plus fort au cours des 10 derniers mois. Merci à Anthropic, à l'équipe Cursor, à Microsoft et à GitHub.

Aujourd'hui, l'accent est mis sur le déplacement de toute la charge de travail possible vers les modèles locaux d'abord : 1) pour apprendre le développement d'IA souveraine, les modèles, le harnachement, etc. ; 2) pour être indépendant des modèles frontier et économiser un peu d'argent (pas encore visible).

Dans mon entreprise Lifetime Oy, nous construisons quotidiennement avec des modèles open source locaux. Aujourd'hui, Claude est en veille chaude : lorsqu'une tâche devient trop difficile pour le modèle local, le modèle frontier intervient, fait le gros du travail et rend le travail. Les fondations restent dans le bâtiment. Deuxièmement, GitHub Copilot, qui met à jour mes commits de manière ingénieuse, corrige les derniers problèmes trouvés dans les packages et est un outil vraiment précieux pour gérer plusieurs dépôts git et versions d'installation clientes.

Les pommes de terre

Les modèles changent chaque mois. Les prix changent. Les politiques changent. Le produit doit quand même être construit à travers tout cela.

C'est pourquoi j'ai écrit une douzaine de standards DWS pour protéger le travail. Le Truth Standard tient les affirmations non étayées à l'écart. L'ontologie DWS garde la structure honnête. Les dictionnaires de domaine gardent chaque domaine de connaissance précis. Ensemble, ils donnent de la traçabilité et stoppent le gonflement de l'IA avant qu'il ne se propage.

L'IA souveraine en pratique est une discipline sur ce qui tourne où : les modèles open source locaux portent le travail quotidien, et vous montez vers un modèle frontier seulement lorsque la correction l'exige.

Voici à quoi cela ressemble sur mon bureau, en août 2026. Si vous avez besoin d'aide pour mettre en place un développement basé sur des modèles locaux — DM. Je suis là pour aider.

Mon bureau & flux de travail — août 2026

Notre codage quotidien tourne sur des machines de développement au bureau. Les modèles cloud et frontier n'entrent que lorsque nous les invitons.

La pile actuelle chez Lifetime Oy :

  • Local, chaque jour : OpenCode sur une DGX Spark, modèles servis via Ollama.
  • DeepSeek V4 et Qwen3 Coder pour les modifications rapides.
  • Nemotron-3-Super lorsque le problème nécessite un raisonnement de domaine pour le travail Lifetime World Model.
  • Flux de dépôt et git : GitHub Copilot CLI.
  • Revue cloud : Gemini lit chaque PR — grand contexte, multimodal, une porte de qualité obligatoire avant toute fusion.
  • Escalade uniquement : Claude Code pour les décisions architecturales difficiles. Veille chaude, pas pilote quotidien.

L'ordre compte plus que les outils. Local est la norme. L'humain dans la boucle est le devoir HIC. Chaque service cloud doit justifier son niveau et son travail, et tout ce qu'il touche a déjà passé un humain de ce côté du fil. Les portes de qualité sont réelles.

J'ai écrit KYA-S1 — v1.5 est un brouillon de spécification normative avec une fenêtre de commentaires publics ouverte — et je construis DWS IQ dessus. KYA v2 est en développement et prévue pour publication plus tard cette année.

Nous appliquons nos propres règles de souveraineté avant de demander à quiconque de le faire.
