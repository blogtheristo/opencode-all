ThinkingBox: Auditing Agents Where They Matter

Risto Anton Päärni — 2026-09-19

The Silent Failure Problem

Your agents run. The transcript looks good. The user says "thanks." Then you check the database, the API logs, the side effects—and nothing happened. The agent hallucinated success.

This is the gap between saying you did something and doing it. Many evaluations still check the transcript or the function call, not whether the work got done.

For revenue engines—outbound campaigns, lead enrichment, targeting refinement, attribution—silent failures are not edge cases. They are existential. One agent that reports "campaign deployed" when nothing shipped, and your GTM burns credibility with one customer. One lead-enrichment agent that hallucinates new contact fields, and your sales team is chasing ghosts.

Microsoft built ThinkingBox to solve exactly this problem. At Lifetime, we have forked the repository to run it against our own agents.

What ThinkingBox Does

ThinkingBox runs agents in isolated, stateful tool environments via MCP (Model Context Protocol) servers. Each conversation spawns isolated tool processes with stdio transport—ensuring every test case runs in a clean, reproducible sandbox.

The architecture inspects three things that transcript-only evals miss:

Stateful Workflows

Real tool use is stateful—create a resource, update it, query the result. Most evals run single-turn calls. ThinkingBox lets agents execute multi-step workflows (call the API, check the response, retry or adapt) and inspects what the tools actually changed.

Simulated Users

Agents often ask clarifying questions. ThinkingBox simulates user responses (via LLM or prompt-driven) and verifies the agent's final answer matches the spec. Single-turn evals miss this entirely.

Side Effect Inspection

The real signal is not "the agent said it worked." It is "the database shows the change," "the API returned success," or "the file was created." ThinkingBox inspects state before and after, flagging hallucinations where the agent claimed success but the tools show failure.

ThinkingBox-Bench: 507 Real Workflows

Microsoft's ThinkingBox-Bench has 507 executable tasks across five business domains: retail and e-commerce, travel and hospitality, auto insurance, internal IT support at a neobank, and IT and HR support at a consulting firm. [1, 2]

The numbers are the argument. The strongest model in the paper passes 65 % of tasks on the first try and solves 91 % at least once in twenty attempts, but gets only 25 % right in all twenty. [1] One success is not reliability.

Each task comes with expected outcomes and isolated MCP tool sessions. You run your agent against it and get a pass/fail on actual side effects—not transcript sentiment.

Local First, on DGX

Our agent workloads default to local compute on DGX; cloud agents are secondary and need a documented reason. Running 507 tasks × 20 attempts in the cloud is expensive, so we are bringing the bench to the DGX, isolated from production data. That runner is work in progress, not yet a shipped configuration.

For Founders & Teams

If you are building agent systems:

  • Investors ask: "How do you know your agents work?" A green ThinkingBox-Bench run is the answer. It is auditable, reproducible, and measures outcomes—not hallucination.
  • Your team needs confidence: One agent that fails silently costs more than a day of eval infrastructure. ThinkingBox catches it before deployment.
  • Revenue engines are binary: Your enrichment agent either enriched the lead or it did not. Your outbound agent either deployed the campaign or it lied about it. ThinkingBox makes that signal clear.

Get Started

DWS-ThinkingBox is our fork of the Microsoft ThinkingBox framework:

  • Lifetime Fork: github.com/blogtheristo/dws-thinkingbox — our working fork
  • Upstream Framework: github.com/microsoft/thinkingbox — the evaluation harness and process isolation layer

Integration Workflow:

  1. Clone Microsoft's harness (or our fork) alongside your agent infrastructure.
  2. Define tool mocks as MCP servers (Python subprocess or HTTP).
  3. Write scenarios and test cases in YAML.
  4. Run tb infer against ThinkingBox-Bench with your agent.
  5. Each test spawns isolated tool processes, runs the agent, collects traces, and verifies outcomes.
  6. Use bench results as CI gates and investor-facing audit trails.

The transcript is what users see. ThinkingBox is what actually happened.

From Eval to Production: The Full Picture

ThinkingBox validates agents before deployment. Once live, the DWS Dashboard monitors them in production—with full observability powered by Aspire.

Operational Pipeline

  1. ThinkingBox-Bench: Pass/fail on the bench's tasks.
  2. Deploy: Push verified agents to production on DGX.
  3. DWS Dashboard: Real-time agent monitoring across three dedicated views:
  • Digital Office: Visual agent workstation status.
  • Control Room: NOC-style grid tracking CPU, memory, task progress, and cost per request.
  • Situation Room: Executive alerts and confidence drift timeline.

Aspire Telemetry: Optional distributed tracing feeding the Control Room with:

  • Agent decision traces (model inputs, tool calls, outputs).
  • Tool latency and error rates.
  • Token usage and cost tracking per agent.
  • MCP server health and performance metrics.
  • End-to-end workflow tracing across multi-agent handoffs.

Real-World Use Case: Control Room Monitoring at Scale

Imagine deploying 50 agents, and one starts hallucinating subtly on Tuesdays. Without traces, your team debugs blind. With Aspire feeding the Control Room:

  • The confidence drift detector flags the anomaly.
  • Detailed agent traces show precisely which tool calls diverged.
  • You pinpoint the model temperature or prompt change responsible for the drift.
  • Rollback or code fix starts from evidence instead of guesswork.
