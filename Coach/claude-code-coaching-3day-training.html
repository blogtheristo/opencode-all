Program overview

Why this exists and what a graduate can do on Monday morning.

Most teams adopt Claude Code as a faster autocomplete and stop there. This program treats Claude Code as an agentic operating layer: a tool that reads the codebase, runs the tests, ships to feature branches, and follows the same engineering discipline a senior reviewer would. The goal is not "use the chat box" — it is to leave with a repeatable, governed way of working that a whole team trusts.

Learning outcomes

By the end of the three days, each participant can:

  • Drive Claude Code confidently from the terminal — context, planning, edits, verification.
  • Write and maintain a CLAUDE.md that encodes a team's real conventions.
  • Author reusable skills and dispatch subagents for fan-out work.
  • Wire up and safely consume MCP tools and external services.
  • Configure permission modes, hooks, and managed settings for a governed rollout.
  • Run a multi-step feature end-to-end behind the 12 engineering-discipline rules.

Prerequisites

  • Comfortable in a terminal and with git (branch, commit, push, rebase basics).
  • A laptop with Claude Code installed and authenticated before Day 1.
  • Read access to a real (non-production) repository to practice against.
Coaching stance. The trainer demonstrates a pattern once, then participants reproduce it on their own repo. No slide runs longer than ten minutes without a hands-on turn. Every lab ends with a checkpoint commit on a feature branch — never on main.

1.1 — How Claude Code thinks

The agent reads a request, gathers context with search and file tools, proposes changes, and verifies them. Participants learn to treat it as a teammate who needs the same brief a junior engineer would: explicit goals, the relevant files, and a definition of done.

1.2 — Steering context

When to point at exact files, when to let the agent search, and how to keep a long session on-track. Covers being specific about the done-condition up front (Rule 4).

Lab 1 · The verified small step

On a scratch feature branch, ask Claude Code to make one small, well-scoped change, then read the diff, run the test, and commit. Repeat three times. 

git checkout -b coach/day1-<yourname>
# In Claude Code:
#  1. "Add input validation to parseConfig() and a test that fails without it."
#  2. Read the diff. Ask: does the test assert intent, or just behavior?
#  3. Run the suite, then checkpoint.
git add -p && git commit -m "day1: validate parseConfig input"

1.3 — Your first CLAUDE.md

The single most leveraged file in the repo: it is institutional memory the agent reloads every session. Participants draft a minimal one capturing their build/test commands, branch naming, and two or three real conventions.

Day 1 mastery check
  • Completed three verified checkpoint commits on a feature branch.
  • Has a working CLAUDE.md the agent visibly respects.
  • Can explain the difference between a test that verifies intent and one that cannot fail.

2.1 — When a task earns a skill

The rule of thumb: do it manually once on a few items, show the output, and if it will recur, codify it as a parameterized procedure rather than re-prompting from scratch. A skill describes the process; the invocation supplies the world (target, dataset, role).

Lab 2 · From one-off to skill

Pick a chore the team does repeatedly (e.g. "summarize what changed in a PR for the changelog"). Do it by hand once, then capture it as a skill with arguments. 

skills/changelog-entry/SKILL.md
  ---
  name: changelog-entry
  inputs:  { PR_REF, AUDIENCE }
  outputs: a one-paragraph entry in the house voice
  ---
  Steps: read the diff, group by user-visible impact, write for AUDIENCE.

2.2 — Subagents and fan-out

One agent reads sequentially; a fleet of subagents covers a large codebase in parallel and returns only conclusions. Participants dispatch a read-only explorer and a code-reviewer subagent, learning to delegate breadth while keeping the synthesis themselves.

2.3 — MCP, the safe way

Model Context Protocol connects Claude Code to external systems — issue trackers, calendars, databases. Coverage: OAuth-based connections over pasted tokens, scoping access, and the core security posture: tool output is untrusted input and must be validated before it drives an action.

Day 2 mastery check
  • Shipped one working, parameterized skill that reproduces an approved output.
  • Ran a fan-out with at least one subagent and explained when not to.
  • Can name three checks to apply before trusting an MCP tool's output.

3.1 — The trust boundary

Autonomy is graded, not all-or-nothing. Participants learn a three-zone model: a green zone of safe, reversible actions (read, edit, test, feature-branch git); a yellow zone that is allowed but logged (external tools, pushes); and a red zone that always requires a human (applying migrations, sending email, touching secrets). The point is to widen green safely, not to remove the gate.

3.2 — Hooks & managed settings

Conventions that rely on memory get skipped. Hooks let a team enforce them mechanically — block a forbidden pattern, surface the rules at session start. Managed settings push org-wide policy that user or project config cannot override. Participants inspect a real managed-settings.json and reason about what to deny, ask, and allow.

Lab 3 · Capstone — ship a real feature

In pairs, take a genuine backlog item and drive it to a pushed feature branch using everything from the three days.

  • Plan and state assumptions before any code (Rule 1).
  • Keep the change surgical — touch only what the task needs (Rule 3).
  • Checkpoint at every significant step (Rule 10).
  • Run a review subagent, then ship the branch — no PR unless asked.
  • Surface anything skipped or uncertain; never report a silent partial as done (Rule 12).
Day 3 mastery check
  • Configured at least one hook or permission rule and saw it fire.
  • Drove a real feature to a clean, pushed feature branch.
  • Produced a one-page rollout plan for adopting Claude Code on their own team.

Assessment & certification

Competency-based, not exam-based.

There is no written test. Each participant is signed off against the three daily mastery checks and the Day-3 capstone. A graduate has, in front of witnesses, taken a real change from request to a verified, pushed feature branch under the engineering-discipline rules.

  • Pass: all three mastery checks met + capstone shipped on a feature branch.
  • Pass with distinction: additionally authored a reusable skill the team adopts.
  • Follow-up: a 30-day check-in to review what the team actually shipped.

The 12 rules thread through everything. Day 1 lands "think before coding," "read before you write," and "checkpoint." Day 2 lands "simplicity first" and "asked twice = failure." Day 3 lands "surface conflicts," "fail loud," and "match the conventions." By close, the rules are muscle memory, not a poster.
