## How it fits our DGX Spark (the DWS environment)

**Our Spark today** — `docs/CLOUD_ENVIRONMENTS.md` §3.2.2 + `infrastructure/dgx-spark/docker-compose.yml` v1.6.0:

- Acer Veriton GN100, GB10, 128 GB unified, ARM64, CUDA 13-capable, ATS mode expected (`nvidia-smi -q | grep -i "addressing mode"` → `ATS`). This is the **primary 24/7 runtime** (31 daily + 16 weekly jobs via `day-runner.sh`); Cloud Run is secondary/staging.
- Services on box: `dws-backend` (Express + all agents + node-cron), `dws-cron`, `dws-postgres` (Tier-1 internal-ops, no host port, `service_healthy`), `dws-temporal` + worker (internal-only), `aspire-dashboard:13.4.6`, `bumblebee-collector`, plus **host Ollama on :11434** (`nemotron-3-super`, `qwen3-coder:30b` primary per `opencode.json`).
- Ollama models compete for the same unified 128 GB as any ExLlamaV3 resident set. The host has no second 128 GB to spare.

**Fit arithmetic:**

- 107 GiB (text-model resident) + ~14 GiB drafter file extents in page cache (reclaimable but occupying unified memory) ≈ **121 GiB occupant** before KV cache at `CTX=6144`. Measured `MemAvailable ~5 GiB` confirms zero headroom.
- You **cannot** co-run `qwen3-coder:30b` (~19 GB) or `nemotron-3-super` alongside this pack. The operator must **stop Ollama or pin its models out** for the duration of the DeepSeek session.
- `dws-backend`/`dws-cron`/`postgres`/`temporal` are lightweight vs model but not zero — any concurrent `day-runner` burst risks reclaim pressure on the drafter's page-cache extents → thrash.
- 40 s load is excellent for a 552B+196B MOE but is not "serverless" — first-token after reboot still pays it; systemd health checks must tolerate it.

**Quality read for DWS workloads:**

- This is a **frontier reasoning/code model** at single-box cost. 97.9% code next-token agreement with 0.054 code KLD is the strongest signal — code and reasoning lose least when halving experts; open-ended general text loses most (0.409 KLD). That matches our agent workloads (material-oracle, schedule-genius, compliance) where structured reasoning matters more than chatty prose.
- 1.59bpw is **not** the whole-checkpoint average (model-wide ~3.46 bits/param when dividing 330 GB by ~763B params). Fair comparison is vs 3.30bpw sibling (224.9 GB experts, KLD 0.091) — 2× bytes for ~½ KLD.

## Recommendation for Lifetime / DWS

**Do not replace the current Ollama primary yet. Run DeepSeek V4.1-Flash 1.59bpw as an isolated pilot service on the same Spark, with memory fencing, and decide on promotion only after TabbyAPI + >6144ctx validation.**

### Tiered recommendation

| Tier | Action | Rationale |
|------|--------|-----------|
| **Now — Pilot (2 weeks, isolated)** | Deploy native ExLlamaV3 TP1 as a **separate systemd unit or Docker profile** (`excluded` from default `docker-compose.yml` bring-up), binding only when scheduled. Stop `ollama` service during pilot windows; enforce `MemAvailable` pre-flight from `scripts/run_tp1.sh`. Validate `CTX=6144` → 8192/16384 and TabbyAPI `draft_mode: mtp` E2E. | Proves 17.5/24.7 claim in our box without endangering `dws-backend` stability; ~0 € marginal cost respects `DWS_COST_POLICY_STANDARD.md` DGX-first. |
| **Next — Gateway** | If pilot stable, expose via LiteLLM router (`docs/field-notes/2026-09-18-dgx-ollama-litellm-router.md` pattern) as `deepseek-v4.1-flash-exl3:1.59` alongside `qwen3-coder:30b`, with **mutual exclusion** (only one resident at a time) until we prove reclaim-safe sharing. | Keeps agent `small_model`/`model` routing intact; avoids silent OOM. |
| **Later — Scale** | Evaluate **vLLM + vllm-exl3 TP2/TP4** path (second Spark) for concurrent serving (Ollama + DeepSeek together) or larger context. Native ExLlamaV3 will **not** give multi-host TP. | Single-Host TP ceiling is hard; multi-box needs vLLM. |
| **Do not** | Copy this pack wholesale into `dws-backend` image, pin Ollama + DeepSeek together, or publish TabbyAPI as GA before E2E bench. | 5 GiB headroom + unvalidated API + non-uploaded 64-byte snapshot = predictable outage. |

### Practical wiring for pilot (copy-paste)

```bash
# 1. Confirm ATS (skip if not ATS — this recipe does not apply)
nvidia-smi -q | grep -i "addressing mode"
# expected: Addressing Mode : ATS

# 2. Build the exact fork (aarch64 Grace needs pause/AVX stub patch)
git clone https://github.com/vcruz305/exllamav3.git && cd exllamav3
git checkout 954a8ca6e59d
python3 -m venv ~/venvs/exl3_v41 && source ~/venvs/exl3_v41/bin/activate
python3 util/patch_exllamav3_aarch64.py exllamav3/exllamav3_ext 2>/dev/null || \
  python3 tools/patch_exllamav3_aarch64.py exllamav3/exllamav3_ext  # alt path in vllm-exl3
CUDA_HOME=/usr/local/cuda-13.0 TORCH_CUDA_ARCH_LIST=12.1a MAX_JOBS=8 \
  pip install --no-build-isolation --no-deps .
python3 -c "import exllamav3, exllamav3_ext; print('ok')"

# 3. Fetch pack (307.7 GiB) + re-lay for ATS zero-copy
huggingface-cli download vcruz305/DSV4.1-Flash-SAGE-EXL3-1.59bpw --local-dir /models/DSV4.1-Flash-SAGE-EXL3-1.59bpw
python util/align_safetensors.py /models/DSV4.1-Flash-SAGE-EXL3-1.59bpw /models/DSV4.1-Flash-SAGE-EXL3-1.59bpw-a64 \
  --align 64 --min-bytes 1048576 --skip .engram.embed. --jobs 4

# 4. Run — the placement that actually fits
export EXL3_ATS_MMAP=1
export EXL3_ATS_COPY='^(?!mtp\.)'
export EXL3_DSPARK_CONF=0.7
export CHUNK=2048
export CTX=6144
bash one-spark-tp1/scripts/run_tp1.sh  # includes MemAvailable pre-flight

# 5. Isolate on DGX — stop competing resident
sudo systemctl stop ollama  # or: docker compose stop dws-backend dws-cron # if co-located
```

Reproduce benches via `one-spark-tp1/BENCHMARKS.md` scripts; publish cold + warm separately. Invite repro per author: PRs welcome on `vcruz305/DeepSeek-V4.1-Flash-EXL3-DGX-Spark-recipe`.

### Risks & open questions to close in pilot

- **Memory reclaim variance** — drafter lives in page cache; `dws-backend` burst could reclaim it mid-decode. Measure `sar -B` / `cat /proc/meminfo` during concurrent cron window.
- **Context ceiling** — only 6144 validated; our compliance prompts can exceed it. Pilot must test 8k/16k before any agent promotion.
- **API surface** — TabbyAPI guidance only; LiteLLM compatibility, streaming, tool-call parser (`deepseekv4`) not validated on Spark.
- **Non-published snapshot** — bench used local 64-byte re-lay not on HF; pin your re-lay hash and keep source shards (symlinked, not copied).
- **Greedy reproducibility** — `EXL3_MOE_MIXED_BSZ1=1` was 5% faster but non-deterministic greedy — stay off.

## Why Win11 shows OpenCode 1.18.16 (and DGX does not)

Two different artifacts share the name *opencode* — this is the confusion:

| Artifact | What it is | Where version lives | Current in this repo |
|----------|------------|---------------------|----------------------|
| **opencode IDE / CLI binary** | The `opencode` binary (`~/.opencode/bin/opencode`, SST/anomalyco distribution, `opencode.ai`) — handles MCP, TUI, sessions | `opencode --version` from shell | **DGX Spark host: 1.18.32** (`/home/admin100/.opencode/bin/opencode`, 2026-09-21, latest as of 2026-09-24). Win11 in your paste: **1.18.16** (2026-08-10) — 6 releases / ~42 days behind (1.18.17→1.18.32). Not auto-updated. |
| **opencode-all (repo)** | Git submodule at `opencode-all/` (our DWS fork of `anomalyco/opencode`) — source, patches, `opencode.json` instructions | `opencode-all/package.json` `version` | **1.18.29** on `dev` branch (HEAD `f14645`), already `git pull origin dev` up-to-date per `opencode:update` script. |

`npm run opencode:update` (`package.json:75`: `cd opencode-all && git pull origin dev`) **only** updates the *repo*, not the *binary*. `npm run opencode:check` validates install.

### Update commands

**Win11 (your PowerShell, 1.18.16 → latest):**

```powershell
opencode --version
# pick one installer you originally used — they do not auto-promote each other:
npm i -g opencode-ai@latest        # npm
scoop update opencode              # Scoop
choco upgrade opencode             # Chocolatey
mise use -g opencode@latest        # mise
# or download: https://opencode.ai/download  /  https://github.com/anomalyco/opencode/releases
opencode --version                 # verify → 1.18.32 (latest 2026-09-21)
```

**DGX Spark / Linux (already current):**

```bash
~/.opencode/bin/opencode --version   # → 1.18.32 (host binary, latest)
cat opencode-all/package.json | grep version  # → 1.18.29 (repo, tracks dev)
npm run opencode:update              # repo: git pull origin dev
npm run opencode:check               # validates dws-gateway-local MCP
```

Chocolatey lags badly (last approved ~1.3.x) — prefer `npm`/`scoop`/`mise`/`brew` for Windows freshness. If you installed via the desktop installer, use its in-app updater rather than npm.
