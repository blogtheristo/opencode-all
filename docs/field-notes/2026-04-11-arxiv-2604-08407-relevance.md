## 1. Paper Summary

**Title:** Your Agent Is Mine: Measuring Malicious Intermediary Attacks on the LLM Supply Chain
**Submitted:** April 9, 2026 (arXiv:2604.08407)

### 1.1 Problem

LLM agents increasingly route their API calls through third-party proxy routers that aggregate
access to multiple upstream LLM providers. These intermediary routers operate at the application
layer with full plaintext access to every request and response payload. No upstream provider
(Anthropic, OpenAI, Google, Groq) currently enforces cryptographic integrity between client and
the upstream model — making the router a trusted-but-unverified position in the trust chain.

### 1.2 Attack Taxonomy

| Class  | Name                          | Description                                                                 |
| ------ | ----------------------------- | --------------------------------------------------------------------------- |
| AC-1   | Payload injection             | Router rewrites LLM response to inject malicious tool calls or instructions |
| AC-2   | Secret exfiltration           | Router extracts API keys, tokens, or env vars from request payloads         |
| AC-1.a | Dependency-targeted injection | Targets specific tool schemas to avoid detection (adaptive evasion)         |
| AC-1.b | Conditional delivery          | Injects only under specific triggering conditions — evades research probes  |

### 1.3 Empirical Measurement

The authors surveyed 428 routers:

- 28 paid (from Taobao, Xianyu, Shopify storefronts)
- 400 free (from public communities)

Findings:

- **9 routers actively injecting malicious code** (1 paid + 8 free)
- **2 routers using adaptive evasion** (AC-1.b conditional delivery)
- **17 routers touched researcher-owned AWS canary credentials** — confirming AC-2 is active in
  the wild (4.0% of surveyed routers exfiltrated credentials)

### 1.4 Real-World Context: LiteLLM Incident (March 2026)

The paper was submitted directly after the March 2026 LiteLLM supply chain compromise, in which
attackers used dependency confusion to inject malicious code into LiteLLM's request-handling
pipeline. Every production deployment that pulled the poisoned release routed LLM calls through
attacker-controlled code with full access to in-flight payloads. This is AC-1 + AC-2 in practice.

### 1.5 Defenses Evaluated

The authors built "Mine" — a research proxy implementing all four attack classes — and evaluated
three client-side defenses deployable without provider cooperation:

| Defense                        | Mechanism                                                         | Effectiveness                                                                        |
| ------------------------------ | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Tool policy gate (fail-closed) | Whitelist allowed tool schemas; reject unexpected outputs         | Blocks AC-1 + AC-1.a at 1.0% false positives — strongest defense for high-risk tools |
| Response anomaly screening     | Heuristic detection of injected content in LLM responses          | Flags 89% of AC-1 samples — useful when fail-closed policy is impractical            |
| Append-only transparency log   | Records all LLM request/response pairs with provider + request-id | Does not prevent attacks; preserves forensic scope evidence after compromise         |

## The Story

This paper matters to DWS6 because it turns a commonly hand-waved infrastructure risk into a
measurable control failure: an intermediary between our application and the model provider can
silently exfiltrate prompts, tamper with outputs, or manipulate tool calls. For DWS6, that means
KYA/KB protections cannot stop at prompt content and provider trust alone; they must also cover
the delivery path between our backend and the upstream model API.

## The Insight

## 2. DWS6 Relevance Assessment

### 2.1 Does DWS6 Use LLM API Routers?

DWS6 uses Claude (primary), Groq, and Google Gemini via official provider SDKs. If any
deployment layer (e.g., LiteLLM for multi-provider routing) sits between the DWS backend and
the upstream provider, the full attack surface applies.

## Next Steps

**Action item:** Audit `src/` for any LiteLLM, OpenRouter, or community proxy imports.
Confirm all LLM client instantiations use official provider SDKs at pinned versions.

### 2.2 KYA 5-Layer Framework — Supply Chain Gap

KYA currently monitors:

- L1: Human KYC (Shufti Pro identity verification)
- L2: Agent provenance (registration gates)
- L3: Capability review (permission gating)
- L4: Runtime behavioral monitoring (ATS scoring)
- L5: Continuous risk assessment (IDV signals, webhook triggers)

**Gap:** None of the five layers covers the _LLM API supply chain_. An agent that passes all
five KYA layers could still receive injected instructions via a compromised router — because
AC-1 delivers malicious content _as a valid LLM response_, not as agent misbehavior. KYA's L4
behavioral monitoring observes what the agent _does_ (tool calls, side effects), not what the
LLM _told_ it to do.

A compromised router could:

1. Inject a `dws kya snap` command into an LLM response → agent executes it with agent-level
   permissions
2. Exfiltrate `ADMIN_API_KEY` or provider API keys if they appear in the system prompt or
   tool-call context
3. Override KB compile output by injecting content before `kb_write_article` is called

### 2.3 KB Autoresearch Pipeline — Specific Target

`dws kb research` drives LLM API calls to compile raw sources into `kb/wiki/` articles. The
output is treated as authoritative internal knowledge. If LLM calls are intercepted mid-flight,
injected content could be written to `kb/wiki/` by the KB agent and subsequently used by
`dws kb ask` and `dws kb compile` as internal facts.

The paper's defense #2 (response anomaly screening) applies directly here: before the KB agent
writes any article to `kb/wiki/`, screen the LLM response for injected shell commands,
credential patterns, or path traversal sequences.

### 2.4 Defense Mapping

| Paper defense              | DWS6 analog                | Gap                                                                                           |
| -------------------------- | -------------------------- | --------------------------------------------------------------------------------------------- |
| Tool policy gate           | KYA permission gating (L3) | KYA gates agent→tool calls, not LLM→agent _responses_                                         |
| Transparency log           | Sovereignty audit logging  | Sovereignty audit logs agent _actions_, not LLM API call provenance (provider, request-id, response hash) |
| Response anomaly screening | Not implemented            | No equivalent in DWS6 today                                                                   |

## 3. Proposed Standards Update (For Human Review — NOT Auto-Applied)

### 3.1 DWS_SECURITY_STANDARD §18.8 (Proposed Addition)

Proposed location: between §18.7 (NIS2 Compliance Statement) and §19.

```markdown
### 18.8 LLM Supply Chain Trust Boundary

DWS IQ routes agent LLM calls to Anthropic Claude (primary), Groq, and Google Gemini. Any
intermediary routing layer (e.g., LiteLLM, OpenRouter, or third-party API proxies) that sits
between the DWS backend and the upstream LLM provider introduces the attack surface described
in "Your Agent Is Mine" (arXiv:2604.08407, April 2026): payload injection (AC-1) and secret
exfiltration (AC-2).

| Control                        | Requirement                                                                                                                                                                                                                         | Enforcement                                                                           |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Direct API only                | LLM API calls MUST go directly to the upstream provider SDK. No opaque intermediary routers without a security review.                                                                                                              | Code review gate on any new LLM client instantiation                                  |
| Provider SDK pinning           | Use only official provider SDKs (`@anthropic-ai/sdk`, `@google/generative-ai`, `groq-sdk`) at pinned versions — no community wrapper libraries                                                                                      | Dependency Security Review CI check                                                   |
| LLM response provenance        | All LLM API calls MUST log provider, model, request-id, and response hash to sovereignty audit log                                                                                                                                  | Enforcement: `src/agents/llm-client.ts` wrapper (required for all new LLM call sites) |
| KB compile response gate       | Before writing to `kb/wiki/`, screen LLM output for injected shell commands, credential patterns, and path traversal sequences                                                                                                      | `kb.agent.ts` pre-write gate (TODO: implement — see §3.2 below)                       |
| Supply chain incident response | If upstream provider SDK is compromised: isolate the affected LLM client, rotate all `ADMIN_API_KEY` and provider API keys, file a field note, trigger `dws kya snap` for any active agent sessions that used the affected provider | Incident runbook reference: `docs/field-notes/`                                       |

Cross-reference: Section 12 (Supply Chain Integrity Policy) — extends package-level supply
chain rules to the LLM API call layer.

NIS2 relevance: NIS2 Article 21(2)(e) — security in network and information systems
acquisition, development and maintenance.
```

### 3.2 Recommended Implementation (Non-Blocking — Propose for Next Sprint)

1. **Audit LLM client instantiations** — `grep -r "litellm\|openrouter\|new LLM(" src/` to
   confirm no opaque proxy is in use.
2. **Add LLM response provenance to sovereignty audit log** — extend `src/agents/llm-client.ts` (or
   equivalent) to log `{provider, model, requestId, responseHash, agentId, timestamp}` to
   sovereignty_audit table.
3. **KB response screening gate** — add a `screener.ts` module in `src/agents/` that runs
   before `kb_write_article`. Fail-closed on: shell command patterns (`\$\(`, `` ` ``, `|`),
   credential patterns (key-looking strings), path traversal (`../`).
4. **Dependency lock audit** — verify `package-lock.json` pins `@anthropic-ai/sdk`, `groq-sdk`,
   `@google/generative-ai` at known-good commit SHAs, not floating semver ranges.
