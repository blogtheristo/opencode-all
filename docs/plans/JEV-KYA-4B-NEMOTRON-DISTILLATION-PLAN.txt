================================================================================
PHASE 1: TEACHER INFERENCE (Synthetic Data Generation)
================================================================================

Duration: 6–8 hours
GPU Memory: ~340 GB (Nemotron-4-340B-Instruct in FP8 + KV cache)
Throughput: Hundreds of thousands tokens/second

OBJECTIVE:
Generate 100K–200K synthetic KYA scenarios across 10 archetypes:
  1. Mandate verdicts (allow/deny/escalate)
  2. Attestation validation (pass/fail/audit)
  3. Risk scoring (high/medium/low)
  4. Model routing (A vs. B vs. C)
  5. Access control (self-serve / require-approval / block)
  6. Confidence calibration (trigger audit if < 0.8)
  7. Concurrency limits (scale down / normal / aggressive)
  8. Latency compliance (within SLA / degraded / alert)
  9. Rate limiting (allow / queue / reject)
  10. Anomaly detection (benign / suspicious / malicious)

CONFIGURATION:
  • Load Nemotron-4-340B-Instruct (NVIDIA Instruct-tuned version)
  • Use vLLM or TensorRT-LLM for serving
  • Leverage Blackwell FP8 native support: 340GB → 170GB in FP8
  • Remaining GPU VRAM reserved for massive KV cache
  • Batch mode: set max_num_batched_tokens to maximum

EXECUTION:
  1. Configure teacher inference pipeline
  2. Generate synthetic (Prompt, Decision, Confidence) triplets
  3. Stream output to disk as .jsonl (one example per line)
  4. Log generation statistics: total examples, token count, archetypes distribution

OUTPUT:
  • File: synthetic-kya-phase1.jsonl (~150K examples)
  • Format: {"prompt": "...", "decision": "...", "confidence": 0.XX}
  • Size: ~500 GB on disk (reduced to 50K after Phase 2)

TEARDOWN:
  • Clear GPU VRAM
  • Verify .jsonl file integrity

================================================================================
PHASE 2: REWARD EVALUATION & CURATION
================================================================================

Duration: 4–5 hours
GPU Memory: ~340 GB (Nemotron-4-340B-Reward in FP8 + KV cache)
Purpose: Filter synthetic data to retain only high-quality examples

OBJECTIVE:
Assign quality scores (0–100) to each synthetic example and filter to top 10–20%

CONFIGURATION:
  • Load Nemotron-4-340B-Reward (NVIDIA reward model)
  • Same FP8 + KV cache strategy as Phase 1

EXECUTION:
  1. Load Phase 1 synthetic dataset (.jsonl)
  2. For each (Prompt, Decision) pair:
     a. Call reward model: score = reward_model(prompt + decision)
     b. Log score
  3. Filter: Keep examples with score ≥ 80 (top 10–20%)
  4. Output filtered dataset

QUALITY CHECKS:
  • Reward score distribution: Log mean, median, std dev
  • Domain purity: Spot-check 100 examples; verify Jev-KYA relevance
  • Curation ratio: If > 50% rejected, investigate noise in Phase 1

OUTPUT:
  • File: kya-sft-training-data.jsonl (~50K curated examples)
  • Format: {"prompt": "...", "decision": "...", "confidence": 0.XX, "reward_score": 0.XX}
  • Size: ~150 GB on disk (reduced proportionally)

TEARDOWN:
  • Clear GPU VRAM
  • Save curated dataset to persistent storage

================================================================================
PHASE 3: STUDENT MODEL TRAINING (SFT + Distillation)
================================================================================

Duration: 2–4 hours
GPU Memory: 8–10 GB (4B model in BF16 + optimizer state)
Purpose: Transfer teacher's Jev-KYA capability to 4B student model

OBJECTIVE:
Train 4B student on curated 50K examples using Supervised Fine-Tuning + KL divergence distillation

CONFIGURATION:
  • Load 4B base model (e.g., Llama-3.2-3B or similar)
  • Full Parameter Fine-Tuning (no LoRA; VRAM abundant)
  • Precision: BF16 (8–10 GB model + optimizer state)
  • Data parallelism: FSDP across DGX GPU cores

EXECUTION:
  1. Split curated dataset: 45K train, 5K validation
  2. Training loop (2–3 epochs):
     a. SFT loss: Cross-entropy on curated labels
     b. Distillation loss: KL divergence between 4B logits and 340B teacher logits
        (Teacher runs zero-shot on same inputs; no retraining needed)
     c. Combined loss: 0.7 * SFT_loss + 0.3 * KL_loss
  3. Hyperparameters:
     • Learning rate: 2e-5
     • Batch size: 32 (adjust for GPU memory)
     • Early stopping: on validation loss (patience=3 epochs)
  4. Monitor: training loss, validation loss, accuracy on held-out KYA types
  5. Save best checkpoint

TRAINING SPEED NOTES:
  • Small model (4B) on large DGX → extremely fast
  • Expected: 2–4 hours for 2–3 epochs on 50K examples
  • Per-epoch time: ~1 hour

VALIDATION TARGETS:
  • Validation accuracy: ≥ 95% of teacher's accuracy (on same examples)
  • Validation loss: Monotonic decrease or plateau (no divergence)
  • Calibration: ECE < 0.10 (measured post-training)

OUTPUT:
  • File: jev-kya-4b-sft-distilled.pt (trained weights in BF16)
  • Size: 8 GB
  • Validation report: accuracy, loss curves, calibration metrics

TEARDOWN:
  • Save trained weights
  • Log validation report

================================================================================
PHASE 4: QUANTIZATION & EDGE DEPLOYMENT
================================================================================

Duration: 1 hour
Purpose: Convert BF16 model to quantized formats for deployment targets

OBJECTIVE:
Export trained 4B model into 3 deployable formats

TARGET A: Mac (Apple Silicon)
  • Format: MLX (compatible with Llama.cpp, Ollama)
  • Quantization: INT4 with group quantization
  • Size: ~2.5 GB
  • Inference: mlx-lm or Ollama on Mac
  • Expected latency: 30–50 ms per token (acceptable for async gates)

TARGET B: Local Agent GPUs (DGX / cloud GPU)
  • Format: vLLM-compatible
  • Quantization: AWQ (Activation-aware Weight Quantization) or FP8
  • Size: ~4 GB (AWQ) or 4 GB (FP8)
  • Inference: vLLM server
  • Expected latency: 8–15 ms per decision (confirmed in prior work)

TARGET C: Edge Systems (Optional)
  • Format: ONNX
  • Quantization: INT8
  • Size: ~1 GB
  • Target: Jetson devices, embedded systems
  • Expected latency: 30–100 ms (device-dependent)

EXECUTION:
  1. Export to MLX:
     python export_mlx.py --model ./trained-4b --quantization int4 --output ./jev-kya-4b-mac
  2. Export to vLLM:
     python export_vllm.py --model ./trained-4b --quantization awq --output ./jev-kya-4b-vllm
  3. (Optional) Export to ONNX:
     python export_onnx.py --model ./trained-4b --quantization int8 --output ./jev-kya-4b-onnx

VALIDATION:
  1. Verify file sizes (MLX ~2.5GB, vLLM ~4GB, ONNX ~1GB)
  2. Load each quantized model; verify inference works
  3. Benchmark latency on target hardware:
     • Mac: Time 1000 decisions on M3 Max (measure p50, p95, p99)
     • Agent GPU: Time 1000 decisions on DGX (measure with vLLM)
  4. Compare accuracy vs. BF16 original:
     • Target: ≥ 98% (INT4 may sacrifice 1–2%)
     • If ≥ 95%, acceptable; log caveat
     • If < 95%, investigate; retry with FP8

OUTPUT:
  • MLX quantized: jev-kya-4b-mac/ (~2.5 GB)
  • vLLM quantized: jev-kya-4b-vllm/ (~4 GB)
  • Optional ONNX: jev-kya-4b-onnx/ (~1 GB)
  • Benchmark report: latency, accuracy, deployment readiness

TEARDOWN:
  • Commit quantized models to repo
  • Document deployment instructions for each target

RISK MITIGATION
================================================================================

RISK: Phase 1 synthetic data is noisy or off-domain
MITIGATION: Phase 2 reward model filters; spot-check 100 examples manually

RISK: Training diverges in Phase 3
MITIGATION: Early stopping on validation loss; conservative LR; proven loss formula

RISK: Quantized model accuracy drops > 5%
MITIGATION: Use lossless AWQ if INT4 shows drops; validate before deployment

RISK: DGX memory pressure during Phase 1
MITIGATION: Monitor VRAM; reduce batch size if needed; pipeline is flexible

RISK: Training data leakage (overfitting)
MITIGATION: Hold out 10% for validation; calibration study (ECE) post-training
