Field Note — 2026-09-22: Workflow v2, Chapters 0–8

1. What happened

Built Workflow v2 — an implementation of the "Procedural Graphs" pattern for long-horizon AI agent tasks — end to end, from engine to nine domain graphs, on branch claude/workflow-v2-procedural-graphs-k2324l (PR #2059).

The problem it solves: an agent running a long, multi-step task tracks its own progress in conversational memory, and conversational memory degrades. The model hallucinates having completed a step it skipped, or loops on a broken tool call. Workflow v2 moves that state out of the chat into an explicit graph the code enforces.

The engine (src/agents/workflow-v2/)

Two roles, per the pattern:

  • Executor — acts only within the current node, and may only transition along edges declared in that node's allowedNext. An illegal transition throws GraphValidationError at runtime; it is not a prompt-level request.
  • Refiner — reads a completed run's ExecutionTrace offline and proposes graph edits for future runs (the self-evolution half of the pattern).

Traces checkpoint to disk after every step. The engine reuses the existing provider-agnostic LLMClient — no new provider wiring.

The hard gate

ApprovalToken / computeApprovalHash / ApprovalRequiredError: a transition leaving a gated node requires a SHA-256 hash binding a human's approval to the exact draft text plus that graph and edge. An approval cannot be replayed against a different draft. Built because CLAUDE.md's RED-zone rule on outbound email must not depend on an LLM choosing to honour a prompt (Discipline rule 12, fail loud).

Phase 1 — KYA-gated typed transitions

runExecutorStepTyped() routes the transition decision through the pre-existing kya-jev primitive (src/agents/kya-jev.ts) instead of regex-parsing prose out of an LLM reply. Two consequences:

  1. A graph run now requires a cryptographically signed KYA verdict to make any transition decision at all — kya-jev refuses to run without one, and a self-constructed {decision:'allowed'} object fails signature verification.
  2. The typed result carries per-option probabilities across every legal next node, which is recorded for the Refiner. A near-even split between two options is a strong signal the node description is ambiguous — exactly what the Refiner's "identify ambiguity" rule is looking for.

2. The insight

Three things are worth keeping from this build.

The gate node id became the contract. Chapters 1, 2, 5, 6 and 8 all reuse the literal node id HIC_APPROVAL_GATE, which DEFAULT_GATED_NODE_IDS in runner.ts already enforces in code. Each new chapter therefore inherited runtime approval enforcement _for free, with no engine change_. That was not designed up front — it emerged from naming the node the same thing twice, and is the single highest-leverage accident in the build.

Not every chapter needs a gate, and forcing one would have been worse. Chapters 3 and 4 are read-only assessments that issue no outbound action. Adding an approval gate would have been cargo-culting the pattern rather than applying it. Recording _why_ they have no gate is more useful than the gate would have been.

Convergent discovery, independently. DWS7_ROADMAP.md Phase 4.1 had already scoped this exact problem months earlier — PR 138 (durable resumable multi-agent workflows, via Temporal.io) and PR 146 (human-in-the-loop approval queue) — with no reference to this work. Separately, Google Cloud's GITEX AI Türkiye framing named the same three goals DWS's own north-star uses. Two unconnected sources converging on one problem shape is a stronger market-timing signal than either alone, which is why it went into the PhD thesis as Key Contribution #60 rather than staying a note.

8. HIC decision question

Which chapter runs for real first, and on which surface?
Chapter 1 (Sales Outreach) is the obvious candidate for revenue, but it means a real
prospect receives a real email through a gate that has never been exercised in
production. Chapter 3 (Compliance Assessment) is read-only and cannot send anything
— it would prove the engine on live data with zero outbound risk, but proves nothing
about the approval gate.
Recommendation: Chapter 3 first as an engine shakedown on real data, then
Chapter 1 once the Mission Control queue exists to catch its gate. Running Chapter 1
before that queue exists means the approval gate has nowhere to surface, and it
would be approved in a terminal — which is exactly the failure mode the placement
decision was made to prevent.
