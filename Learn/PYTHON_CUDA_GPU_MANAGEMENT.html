    • 1. The Problem: GPU Package Hell

    Installing NVIDIA GPU-accelerated Python packages has historically been painful:

  • Navigate to pytorch.org / jax.dev / rapids.ai to find your CUDA version
  • Copy a custom `pip` or `uv` command with a special index URL
  • Use special package names like `nvidia--cu{11|12}`
  • Different packages use different naming conventions (`xgboost` vs `xgboost-cpu`)
  • Overlapping file installs between CPU and GPU variants cause unpredictable behavior
    • Security risk: Suffixed variant packages (e.g. `numpy-cuda`) enable name-squatting supply chain attacks. Scale of the problem: As of 2025-12-05, 552 out of 8,136 (6.8%) of issues on uv's issue tracker contained the term "torch" — largely installation confusion.

    2. The Solution: Wheel Variants (PEP 817 + PEP 825)

    What Are Wheel Variants?

    An extension to the Python binary distribution format that allows:

  • Package maintainers to declare multiple build variants for the same package version
  • Installers to automatically select the most appropriate variant based on system hardware/software

    • Three Pillars

    PillarDescription
    Wheel Variant SystemMultiple wheels for same package version, distinguished by hardware attributes
    Provider Plugin SystemVendor-shipped packages that detect system capabilities (CUDA version, CPU features)
    Hash-based IdentificationEnsures compatibility while maintaining clarity in package naming

    The WheelNext Initiative

    NVIDIA initiated the WheelNext open source project to fix Python packaging for scientific computing, AI, and HPC. Collaborators: NVIDIA, Meta, Astral (uv), Quansight, PyTorch team.

  • Website: wheelnext.dev
  • PEP 817: Wheel Variants — Beyond Platform Tags
  • PEP 825: Wheel Variants — Package Format (split from PEP 817)

    • 3. How It Works — Architecture

    Variant Metadata Format

    Wheels encode "properties" declaring hardware requirements using a declarative format:

    nvidia :: cuda_version_lower_bound :: 12.8
x86_64 :: microarchitecture :: v3

    The syntax uses a 3-element tuple: `namespace :: feature_name :: value`

    Provider Plugins

    Provider plugins are purpose-specific modules that:

  • Detect local software and hardware capabilities
  • Filter incompatible wheel variants
  • Rank remaining variants by preference

    • Example flow with `uv pip install torch`:

  • uv queries available PyTorch variants from the index
  • NVIDIA provider plugin detects local GPU state (CUDA driver version, compute capability)
  • uv cross-references variants with detected capabilities
  • Best-fitting variant is installed automatically

    • Sorting Priority (Three Layers)

  • Provider plugin — default priority defined by the plugin itself
  • Package — variant information embedded in the wheel
  • User — explicit override via install command

    • If `nvidia` namespace has higher priority than `x86_64`, a CUDA variant is preferred over an x86-64-v3 variant.

    PyTorch Variant Example (as of October 2025)

    PyTorch publishes 7 variants per release:

    VariantDescription
    CPU-onlyNull variant (always supported, fallback)
    CUDA ≥12.1Older CUDA runtime
    CUDA ≥12.6Mid-range CUDA
    CUDA ≥12.8Latest CUDA
    ROCm (×2)AMD GPU variants
    XPU (Linux)Intel GPU variant

    4. Installation — The New Way

    Install Variant-Enabled uv

    # Install experimental variant-enabled uv build
curl -LsSf https://astral.sh/uv/install.sh | \
  INSTALLER_DOWNLOAD_URL=https://wheelnext.astral.sh sh

    Install PyTorch (Automatic Detection)

    # The dream: this just works now
uv pip install torch

    # Explicitly select a variant label uv pip install torch#cu128    # Force CUDA 12.8 variant uv pip install torch#sm120    # Target specific GPU architecture

    The `#` syntax allows explicit variant label selection.

    Backward Compatibility

  • Older pip versions that don't understand variants simply ignore them
  • Variant wheel filenames never match the previous Wheel Regex
  • Existing infrastructure continues to work unchanged

    7. Best Practices for Python CUDA Management

    Environment Management

  • Use `uv` over `pip` — faster, better dependency resolution, variant support
  • One venv per project — never install GPU packages globally
  • Pin CUDA version — match your driver's maximum supported CUDA version
  • Use `.python-version` — lock Python version per project

    • CUDA Version Compatibility

    Driver Version → Maximum CUDA Toolkit Version
≥ 555.42       → CUDA 12.5
≥ 560.28       → CUDA 12.6
≥ 565.57       → CUDA 12.8

    Check your driver: `nvidia-smi` (top right shows max CUDA version)

    Troubleshooting

    # Check if CUDA is visible
python -c "import torch; print(torch.cuda.is_available())"

    # Check CUDA version PyTorch was built with python -c "import torch; print(torch.version.cuda)"
    

    # List GPU devices python -c "import torch; [print(f'{i}: {torch.cuda.get_device_name(i)}') for i in range(torch.cuda.device_count())]"
    

    # Monitor GPU usage watch -n 1 nvidia-smi

    8. Key Takeaways

  • Wheel Variants (PEP 817/825) solve the GPU package installation mess
  • `uv pip install torch` will "just work" — no more manual CUDA version matching
  • Provider plugins auto-detect your hardware and select the right binary
  • Backward compatible — existing tools continue to work
  • Security improvement — eliminates the name-squatting attack vector
  • Multi-vendor — supports NVIDIA CUDA, AMD ROCm, Intel XPU, and more
  • Experimental today — PyTorch 2.8+ supports it; expect broad adoption in 2026
