2. What “ready to deploy” means on day 60

Measured on the G0–G10 gates of docs/plans/PRODUCT_PRODUCTION_READINESS_PROGRAM.md:

  • Gates G0–G9 pass for each pilot in scope: lifecycle truth, buyer and outcome, commercial contract, working delivery, agent access, security and sovereignty, verification, operations, fulfilment, product surface.
  • G10 is split. The staging rehearsal part of G10 is done on both targets — a cloud tenant and a customer-owned device (DGX Spark / edge node) — with rollback and an evidence pack. Customer acceptance sign-off needs a signed customer and happens in the pilot itself, after day 60.
  • Conflict to know about: the priority plan (merged 28.09) estimates 8–10 weeks for G0–G9 on all five pilots and 14–18 weeks to deployment evidence. The 60-day target fits G0–G9 plus the staging rehearsal for the first four; it does not fit customer sign-off, and it does not fit LF-ONTOLOGY-PILOT, which the HIC placed last (maturation hold).

3. The delivery model — who does what

Role Who Does Never does
Decides HIC Priorities, pricing, what ships, blog/public text, merges of policy and blog PRs Code
Leads Claude Code (paid) Breaks each gate into task specs with checks that fail today (scripts/loop-task.mjs), reviews loop PRs, fixes CI, watches and merges loop PRs hourly, RED-zone and security work Multi-file coding the loop can do
Builds opencode-loop on the DGX (local models, no paid tokens) Works one spec at a time until scripts/agent-done-gate.mjs --full says DONE, then opens a PR Merging; editing the public site; blog text
Catches up opencode-all Clears the open-PR backlog after days of Claude/Copilot sessions (--status, --prs) New feature work
Gatekeeper agent-done-gate + CI “Done” is a command result: committed, pushed, formatted, typecheck, lint, tests, the task’s own checks —

The loop of one gate: spec (Claude Code) → loop builds (DGX) → gate DONE → PR → CI → review and merge (Claude Code, hourly) → next spec. The HIC sees merges, blocks and questions only.

4. What the first day taught us (28.09.2026)

  • It works at volume. In the first day the loop delivered verification suites for four agents (schedule-genius, material-oracle, seo-audit, sitesense), a KYA audit-record feature and two planning/operations changes; #2209, #2211, #2216, #2219, #2221 and #2222 were merged. Tests written by the loop found three real bugs in schedule-genius.
  • “Done” is only as strong as the gate. The first two loop PRs passed the gate and failed CI lint; the gate did not run ESLint. Lint was added the same day. Rule: the gate must be at least as strict as CI.
  • Checks cannot see scope. One loop PR changed the base agent class outside its task and passed every check. Scope stays a Claude Code review item on every PR.
  • One bad merge blocks everything. A PR merged with lint errors turned main red, and every open PR failed with it until the fix was ported. The hourly watch finds and fixes this; it must keep running for the 60 days.
  • Specs must fail first. A check that already passes proves nothing; loop-task.mjs refuses it.
  • The CI runner is on the DGX, where a local LLM is reachable — tests that assume “no LLM” must pin it, or they pass locally and fail in CI.

5. How we keep the 60 days honest

  • One number per pilot, weekly: gates passed out of G0–G10, from the readiness scorer — not a model’s summary. Reported every Sunday HIC batch.
  • Every gate has a spec in .claude/done/<branch>.json before the loop starts it.
  • Stop rule: if the loop reports BLOCKED twice on the same spec, Claude Code codes it or the HIC reshapes the gate (CLAUDE.md Coding Delegation Rule).
  • Day 30 check (28.10.2026): the three P0 pilots at G0–G6 (the plan’s 4–6 week estimate). If not, the HIC decides whether to cut scope (e.g. DWS-US-PILOT moves after day 60) rather than slip the date.
  • Deployment rehearsal needs hardware: the own-infrastructure target needs a DGX Spark or edge node reserved for staging from about day 45 (12.11.2026).
