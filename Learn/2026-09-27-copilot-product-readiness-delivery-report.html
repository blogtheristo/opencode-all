04Architecture flow — catalogue to fulfilment

One canonical catalogue drives every public surface; one durable order-intent record sits between checkout and payment-provider redirect, so no sale is ever lost even if a provider redirect fails.

Canonical catalogue

dws10.com/config/products.json — single source of price, spec, delivery contract for all 138 SKUs

→

Shared generators

build_store.py, scripts/truth/*, scripts/i18n/products/* render every public surface deterministically

→

Public surfaces

Price list, 5-language detail pages, product-action bar, Firehorse 9-product store — all always payable

→

Durable order intent

Server-priced, idempotent row created before any provider redirect (migration 099, unapplied)

→

Verified payment

Stripe webhook-verified; Revolut/PayPal audited managed verification against provider dashboards

→

Fulfilment

SES buyer + ops alerts, runbook-driven delivery by named chapter owner team

05Durable payment architecture

The payment path treats "paid" and "delivered" as two independently tracked states, and never trusts a client-supplied price.

Payment/fulfilment state machine, in order
StepWhat happensWhere
1. Price computed server-sideCheckout never trusts a client-supplied amount; the canonical catalogue price is looked up on the serversrc/services/product-order.service.ts
2. Durable order intent createdAn idempotent product_order_intents row is written before any redirect to a payment provider — a failed redirect never loses the orderMigration 099_270926_product_order_fulfilment.sql (reviewed, not applied)
3. Pending-review event recordedNotification status/attempt/error columns track buyer and ops emails independently of payment stateSame migration
4. Provider redirectBuyer is sent to Stripe, Revolut or PayPal only after step 2 succeedsdws10.com/checkout/durable-order-intake.js
5a. Stripe pathVerified via signed webhook confirmationsrc/routes/stripe-webhook.routes.ts
5b. Revolut / PayPal pathAudited managed verification — an operator confirms the transaction reference against the provider dashboard before fulfilment startssrc/routes/payment.routes.ts, src/routes/b2b-payment.routes.ts
6. Fulfilment gated on verified paymentFulfilment status only advances from pending once payment is independently verified — never on an unverified transactionsrc/services/product-order.service.ts
7. Buyer + ops notificationAWS SES sends a buyer confirmation and an internal ops alert with SKU, buyer, provider, verified amount and fulfilment statusSame service

06Mandatory deployment sequence

Migration 099 is written and reviewed but deliberately not applied. The order below is mandatory and must not be reordered.

  1. 1Apply migration 099Run 099_270926_product_order_fulfilment.sql against the target Supabase project in a maintenance window.
  2. 2Run the schema preflightnpm run preflight:product-orders — calls RPC product_order_schema_preflight; must exit 0 before proceeding.
  3. 3Deploy the order/payment backendOnly after the preflight passes — a missing migration must fail loudly at deploy time, not silently at checkout time.
  4. 4Deploy checkout / public surfacesPrice list, product pages, Firehorse store and the product-action bar go live last, once the backend they call is confirmed present.
