    2.5 Multi-Agent Systems Theory and Lifetime Scope Signals

    This section introduces a novel theoretical contribution: the Lifetime Scope Signals protocol for multi-agent coordination in bootstrapped industrial AI platforms.

    2.5.1 Multi-Agent Systems Background

    Multi-agent systems (MAS) theory (Wooldridge, 2009) provides the foundation for understanding how autonomous agents can coordinate to achieve complex objectives. Key concepts applied to Firehorse:
  • Agent autonomy: Each agent operates independently within defined responsibility areas
  • Agent communication: Agents exchange signals to coordinate dependencies
  • Emergent behavior: System-level capabilities arise from agent interactions
  • Coordination mechanisms: Protocols ensure agents work toward shared goals

    • 2.5.2 Lifetime Scope Signals Protocol

    The Lifetime Scope Signals protocol is a novel coordination mechanism developed for DWS IQ 6. It enables deterministic multi-agent development coordination. Unlike traditional MAS approaches based on real-time negotiation, this protocol uses declarative signal emission to unblock dependent agents. Signal format: 
    
[AGENT-XX]:SIGNAL_TYPE:MILESTONE:TIMESTAMP
    Signal types: | Type | Meaning | Action | |------|---------|--------| | `READY` | Milestone achieved | Unblocks downstream agents | | `COMPLETE` | All agent work finished | Agent transitions to ready state | | `ERROR` | Agent encountered an error | Alerts coordinator | | `BLOCKED` | Waiting for external dependency | No action until unblocked |

    2.5.3 MCP Hub Orchestration Patterns

    The Model Context Protocol (MCP) Hub (`mcp-hub/server.py`, port 8765) implements four workflow patterns for multi-agent coordination. Each pattern exposes a dedicated HTTP endpoint and handles agent routing, error propagation, and result aggregation. 1. Fan-Out Pattern (`POST /workflow/fan-out`) Distributes tasks to multiple agents in parallel using `asyncio.gather()`. All agents execute concurrently with a shared HTTP client (300s timeout). Exceptions are serialized per-task, enabling partial success — if one agent fails, others still return results. Used for Category B (Operations) agents where tasks are independent. 2. Sequential Pattern (`POST /workflow/sequential`) Executes tasks one by one in dependency order. Each task's result is injected as `context["previous_result"]` into the next task, creating an explicit data flow chain. Suitable for pipelines where output of one agent feeds the next (e.g., data extraction → analysis → report generation). 3. Reflection Pattern (`POST /workflow/reflection`) Implements an iterative implementation-evaluation loop. An implementation agent produces output, an evaluation agent scores it (0.0–1.0) and provides feedback. If the score falls below a configurable threshold (default 0.85), the feedback is injected back into the implementation agent for another iteration (max 3 by default). Used for Category C (Customer-facing) agents where output quality is critical. 4. Pipeline Pattern (`POST /workflow/pipeline`) —     Recommended for production Combines parallel and sequential execution through staged workflows. Each stage contains a list of tasks that execute in parallel (fan-out within stage), while stages execute sequentially (results from stage N flow as context into stage N+1). This avoids the sequential bottleneck while maintaining dependency ordering between logical phases. | Pattern | Parallelism | Context Passing | Best For | |---------|------------|-----------------|----------| | Fan-Out | Full parallel | None | Independent tasks | | Sequential | None | Previous → Next | Dependent chains | | Reflection | None | Feedback loop | Quality-critical output | | Pipeline | Parallel within stages | Stage → Stage | Production workloads |

    2.5.4 Skills and CLIs as Agent Interfaces

    The "Build for Agents" principle establishes that every DWS product must be accessible through three complementary interfaces beyond the GUI: a CLI, an MCP server, and Claude Code Skills. CLI (Command-Line Interface) The CLI (`npx tsx cli/src/cli.ts `) provides structured JSON output for every agent operation. This follows the industry trend where AI agents consume tools through command-line interfaces rather than graphical interfaces. Key commands:
  • `dws agents` — List all registered agents
  • `dws run --input '{...}'` — Execute a named agent with structured input
  • `dws workflow ` — Trigger a multi-agent workflow
    • The CLI-first approach ensures that every feature is automatable, testable, and composable. A product that exists only as GUI is considered incomplete. MCP Server The MCP endpoint (`/mcp`, JSON-RPC 2.0) makes all agents auto-discoverable via `tools/list`. External AI systems (Claude Code, Cursor, VS Code Copilot) can connect to the MCP server and invoke any agent as a tool. This implements the Model Context Protocol specification for standardized tool integration. Claude Code Skills Skills (`.claude/commands/    .md`) are reusable workflow components that encapsulate agent invocations as slash commands. Six production skills are deployed: | Skill | Purpose | |-------|---------| | `/compliance-check` | EU regulatory gap analysis (ETS, CBAM, CSRD) | | `/agent-run` | Execute any named agent with structured input | | `/workflow` | Trigger multi-agent workflows | | `/discover-agents` | Find agents by capability keyword | | `/site-safety` | Construction site safety assessment | | `/carbon-analysis` | Embodied carbon footprint calculation | Each skill is a callable, testable component that combines prompt engineering with tool orchestration. The skill pattern ensures that agent capabilities are accessible without requiring users to understand the underlying MCP protocol or CLI syntax. Three-Interface Rule: Every new agent must ship with all three interfaces (CLI command, MCP tool, Claude Code Skill). This guarantees that agents are usable by humans (CLI), other AI systems (MCP), and within development workflows (Skills).

    6.7 Human-in-the-Loop Learning Pipeline (HIL)

    The DWS6 platform's daily operations are managed through an automated Human-in-the-Loop (HIL) learning pipeline, creating a continuous feedback loop between the developer, AI agents, and the codebase.

    Pipeline Architecture

    
GitHub (source of truth)
    | git pull (daily, automated via Startup-DailySync.bat)
Local repository (Windows)
    | Sync-ToProton.ps1
Proton Drive (encrypted local backup)
    | Generate-PDFs.ps1 -> styled HTML -> Learn/ folder
    | Sync-ToSupabase.ps1
Supabase Storage (EU cloud backup)
    |
Edge browser (morning review of Learn/ folder content)
    | human reads, learns, decides what needs work
Claude Code session (next action)
    | git push
GitHub -> cycle repeats

    Pipeline Components

    | Step | Script | Function | Output | |------|--------|----------|--------| | 1 | `git pull` | Fetch latest changes from GitHub | Updated local repo | | 2 | `Sync-ToProton.ps1` | Copy business files to Proton Drive | Encrypted backup | | 3 | `Generate-PDFs.ps1` | Convert 19 markdown files to styled HTML | `Learn/` folder | | 4 | `Sync-ToSupabase.ps1` | Upload code and documents to Supabase Storage | EU cloud backup | | 5 | Edge browser | Automatically open updated files for review | Human knowledge | | 6 | Claude Code | AI-assisted development session | Code changes | | 7 | `git push` | Push changes to GitHub | Cycle completes |

    Why This Pipeline Matters

    The HIL pipeline solves three critical problems:
  • Knowledge gatekeeper: Every morning, the human reviews the latest state of all business documents. Nothing drifts unnoticed.
  • Three-layer backup: Every change exists in GitHub (version control), Proton Drive (encrypted local), and Supabase (EU cloud). No single point of failure.
  • Continuous learning loop: Human reads -> identifies gaps -> uses Claude Code to fix -> pushes changes -> next morning sees the update. The feedback loop closes daily.

    • 10.13 Claude Code Engineering Structure: AI Workflow as First-Class Engineering

    10.13.1 Motivation

    As Claude Code adoption scales beyond individual experiments, a decisive architectural split emerges: projects treating AI workflows as temporary chat interactions diverge sharply from those engineering them as first-class software components. The DWS6 repository embodies the latter approach, and this section documents the principles that make it work at enterprise scale. The core insight — validated by emerging Claude Code community practice in 2026 — is that the same separation of concerns used in software engineering applies equally to AI workflow design. A prompt is not a product; a skill is.

    10.13.2 CLAUDE.md as Project Memory

    Traditional AI usage repeats context in every prompt, creating two compounding costs: token waste and behavioral drift. The DWS6 solution is `CLAUDE.md` — a living specification file serving as shared institutional memory across all AI sessions and tools. The DWS6 `CLAUDE.md` (2,000+ lines as of v3.17) centralizes: | Category | Content | |----------|---------| | Standards | Brand, Document, Security, Market Research, Gamma UI | | Architecture | Brain-Memory-Body-Hands, dual folder structure, store update rules | | Constraints | File handling (git mv, never delete), public site publishing rules, email rules | | Non-negotiables | EU data residency, GDPR, Article 12 logging, security coding rules | | Guardrails | execFile vs exec, CORS policy, SRI hash enforcement | Measured impact: every new Claude Code session inherits 18 months of architectural decisions with zero human repetition. The VERSION AND AGENT HISTORY block in each document extends this to individual files — every document carries its own modification lineage visible to both humans and agents.

    10.13.3 Skills as Reusable Workflow Components

    The shift from ad-hoc prompting to reusable skills represents a fundamental upgrade: from chat interaction to system design. Skills are composable, versionable workflow components — not one-off prompts. DWS6 implements six production skills in `.claude/commands/`: | Skill | Function | Output | |-------|----------|--------| | `/compliance-check` | EU ETS/CBAM/CSRD gap analysis | Structured compliance report | | `/agent-run` | Execute any named DWS IQ agent | Scored JSON results | | `/workflow` | Trigger multi-agent workflow chains | Unified multi-agent report | | `/discover-agents` | Find agents by capability keyword | Agent capability index | | `/site-safety` | Construction safety assessment (SiteSense) | Score 0–100, EN 13001 warnings | | `/carbon-analysis` | Embodied carbon per EN 15978 LCA | kgCO2e by lifecycle stage | Each skill encapsulates input validation, agent execution, and structured output formatting. Without skills, these workflows require repeated error-prone prompting. With skills, they become callable, testable components — directly implementing the Build for Agents principle: if a capability cannot be invoked as `dws `, it is not shipped.

    10.13.4 Hooks for Automated Workflow Validation

    Hooks are the enforcement layer of AI workflow engineering — and the most underutilized pattern in current practice. Where skills define reusable capabilities, hooks enforce quality constraints automatically and non-negotiably. DWS6 implements hooks at two levels: Claude Code hooks (`.claude/hooks/`):
  • Tool output transformation — normalize agent JSON responses to consistent schema
  • Structured output verification — ensure all CLI commands produce valid JSON
  • Session start validation — verify environment readiness before agent work begins
    • Git hooks (`.githooks/`):
  • Branch name enforcement — `claude/-` naming convention before commit
  • Pre-commit security checks — detect hardcoded secrets, unsafe exec() patterns
    • The critical property of hooks is non-negotiability: unlike CLAUDE.md guidance (which an agent may follow imperfectly), hooks intercept tool calls and either transform or block them. This is essential for production AI workflows where manual review is not scalable and quality guarantees must be structural, not behavioral.

    10.13.5 Subagents and Parallel Execution

    The DWS6 architecture employs specialized subagents for distinct task classes, extending the multi-agent orchestration principle from Firehorse production workflows into the development workflow itself: | Subagent Type | Role | Isolation Property | |---------------|------|--------------------| | Explore | Codebase search, file pattern matching | Protects main context from large result sets | | Plan | Architecture design, trade-off analysis | Returns structured plan without executing changes | | General-purpose | Multi-step research, document analysis | Full tool access for complex investigation | | Background | Independent parallel tasks | Non-blocking; notifies on completion | The isolation property is critical at scale: subagents prevent context window exhaustion on large codebases while enabling parallel execution of independent tasks. The Firehorse production orchestration (Temporal.io + event bus, Section 10.7) extends this same pattern to customer-facing agent workflows.

    Appendix H: Automated PR Workflow (HIL Automation)

    Background

    A key operational challenge for solo developers and small teams managing enterprise-grade codebases is maintaining code quality without a dedicated review team. The Firehorse model addresses this with a fully automated pull request review and merge workflow that replaces manual human-in-the-loop (HIL) code review with dual-model AI review.

    Architecture

    
Claude Code → PR → Claude sanity check → Gemini HIL review → @copilot fixes → CI → auto-merge
                                                ↑                    |
                                                └────────────────────┘  (fix loop)

    Components

    | Component | Role | Technology | |-----------|------|-----------| | Claude Code | Code generation, branch creation, PR opening | Anthropic Claude Opus/Sonnet | | Claude (reviewer) | Quick sanity check: security, correctness, breaking changes | Claude Sonnet 4 API | | Gemini (HIL gate) | Deep review: edge cases, tests, architecture, OWASP security | Gemini 2.0 Flash API | | Copilot coding agent | Implements fix instructions from review comments | GitHub Copilot | | PR Auto-Merge | Merges when all checks pass and AI approves | GitHub Actions + GraphQL |

    Design Decisions

  • Gemini defaults to REQUEST_CHANGES — ensures every PR goes through at least one improvement cycle, even when the original implementation appears correct
  • Dual-model review — two different AI models catch different classes of issues (structural vs. security vs. convention)
  • Automated fix loop — structured fix instructions sent to @copilot, which implements fixes and re-triggers review, reducing developer involvement to final skim (~5 min per PR)
  • Human overrides — `do-not-merge` and `needs-human-review` labels pause automation for manual review when needed

    • Relevance to Thesis

    This workflow demonstrates the Solution Factory model (Section 5) operating at full automation: a single developer with AI agents produces enterprise-quality code at scale. The HIL learning pipeline (Section 6.7) feeds review insights back into agent training, creating a continuous improvement loop that aligns with EU AI Act Article 12 auditability requirements.

    Deployment

    10.14 Agent System Hardening — Production Reliability

    10.14.1 Motivation

    The 31-agent system (13 core + 5 SEO + 13 workflow/industry) had accumulated 6 TypeScript compilation errors and 3 test failures that blocked production builds. These were not design flaws but integration debt: type mismatches across module boundaries, missing route wiring, uninstalled dependencies, and locale-dependent formatting. This section documents the systematic hardening that restored zero-error compilation and full test coverage.

    10.14.2 Type System Alignment: SandboxContext

    The `SandboxStage` type in `src/sandbox/index.ts` defined four stages: `'1' | 'opensandbox' | '2' | '3'`, where `'opensandbox'` represents the Stage 1.5 Docker-based isolation on Acer Veriton GN100 hardware (Section 10.10). However, `SandboxContext.stage` in `src/agents/types.ts` only accepted `'1' | '2' | '3'`, creating a compile-time error when `BaseAgent` attempted to assign the sandbox stage. The fix aligned both types, ensuring agents can execute in all four isolation stages.

    10.14.3 Route Wiring: MCP and Human-in-the-Loop

    Two critical routes were unreachable due to missing imports in `src/app.ts`:
  • MCP Agent Server (`/mcp`) — The `createMCPRouter()` function from `src/mcp/agent-server.ts` exposes all agents as MCP tools via JSON-RPC 2.0. Without this import, external MCP clients (Claude Desktop, other AI agents) could not discover or invoke DWS agents.
  • Human-in-the-Loop (`/api/hil`) — The HIL endpoint enables one-click task completion from morning briefing emails. Without this route, the Captain Pre-Briefing Agent's "Done" buttons returned 404 errors.

    • 10.14.4 Locale-Deterministic Number Formatting

    The Emissions Data Analyst agent formats ETS cost estimates using `Number.toLocaleString()`. On EU-locale machines (Finland, Germany), this produces space-separated numbers (e.g., `2 040 000`), while tests expected US comma-separated format (`2,040,000`). The fix specifies `'en-US'` locale explicitly, ensuring deterministic output regardless of deployment environment. This is critical for EU-hosted Cloud Run instances where system locale defaults to European conventions.

    10.14.5 Dependency Hygiene

    The `luxon` library (timezone-aware date handling for Helsinki business hours) was imported in the Social Scheduler but never added to `package.json`. The Resend email SDK's batch response type was a union (`undefined[] | CreateBatchSuccessResponse`) that required runtime array detection before calling `.map()`.

    10.14.6 Research Contribution

    This hardening session demonstrates a pattern relevant to multi-agent system maintenance: integration debt accumulates at module boundaries, not within modules. Each individual agent was correctly implemented, but the connections between agents, sandbox, routes, and tests had drifted. The fix touched 6 files across 5 subsystems in a single commit, restoring:
  • 0 TypeScript errors (was 6)
  • 47/47 tests passing (was 44/47)
  • Full MCP discoverability for all 31 agents
