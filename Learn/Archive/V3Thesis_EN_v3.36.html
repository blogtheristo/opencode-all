    • 1. Introduction

    1.1 Background

    European industrial SMEs face a "twin transition" challenge:
  • Digital transformation: AI, automation, real-time decision-making
  • Green transformation: EU Fit for 55 (55% emissions reduction by 2030), embodied carbon mandates by 2028
    • Traditional SaaS platforms fail because they:
  • Cost EUR 1,400+/month (unaffordable for SMEs)
  • Require cloud-only architecture (high latency, high operational costs)
  • Do not address industry-specific compliance workflows
    • Firehorse (DWS6) solves this with a novel operating model combining:
  • Free-tier cloud infrastructure (EUR 0-350/month vs EUR 1,400+)
  • Edge AI (NVIDIA Jetson) for <100ms inference
  • Industry-specific AI agents (Construction, Manufacturing, Energy)
  • Phased deployment (Silent Pilot -> Advisor -> Autonomous)
  • E-commerce validation through DWS10.com, Google Merchant Center, and Revolut Business [V3.0]

    2. Theoretical Framework

    2.1 Lean Startup Methodology

    The Lean Startup methodology (Ries, 2011) forms the foundation of Firehorse product development. The core principle of the Build-Measure-Learn cycle directly guides the phased deployment model: Application to Firehorse: | Lean Startup Concept | Firehorse Implementation | | -------------------------------- | -------------------------------------------------------- | | MVP (Minimum Viable Product) | 2 agents (CustomerSat, Viability) for 5 pilot customers | | Validated Learning | Silent Pilot phase observes before acting | | Build-Measure-Learn | Phase 1 -> Phase 2 -> Phase 3 progression | | Pivot or Persevere | Signal-based coordination allows rapid course correction | The Customer Development methodology (Blank, 2013) extends this with the principle of "getting out of the building" - validating product-market fit with real customers before scaling. Firehorse's 2-month payback guarantee operationalizes this by creating a measurable validation metric. Jobs-to-be-Done Framework: Following Clayton Christensen's framework, Firehorse identifies the "job" customers hire the product for:
  • Functional Job: Track embodied carbon for EU compliance (2028 deadline)
  • Emotional Job: Reduce anxiety about regulatory penalties
  • Social Job: Demonstrate sustainability leadership to stakeholders

    2.4 Edge Computing Economics

    Edge computing economics (Shi et al., 2016) provides the theoretical foundation for Firehorse's hybrid architecture. The key insight is that latency and bandwidth costs frequently exceed the savings of centralized processing: Latency-cost tradeoff analysis: | Processing Location | Latency | Monthly Cost | Use Case | | --------------------------- | ------------ | -------------------------- | -------------------------------------- | | Cloud (Groq API) | 500-2000ms | EUR 555/month | Complex reasoning, report generation | | Edge (Jetson Orin Nano) | <100ms | EUR 100/year (electricity) | Real-time construction site monitoring | | Hybrid | Best of both | EUR 25-350/month | Firehorse optimal configuration | Edge AI ROI calculation: 
    
Cloud solution (12 months):
  Compute: EUR 555/month x 12 = EUR 6,660/year
  Total: EUR 6,660/year

Edge AI solution:
  Hardware (one-time): EUR 1,084 (Jetson Orin Nano + accessories)
  Electricity: EUR 10/month x 12 = EUR 120/year
  Year 1 total: EUR 1,204
  Year 2+ total: EUR 120/year

Savings: EUR 5,456/year (82% cheaper)
Payback period: 1.95 months

    2.5.1 Multi-Agent Systems Background

    Multi-agent systems (MAS) theory (Wooldridge, 2009) provides the foundation for understanding how autonomous agents can coordinate to achieve complex objectives. Key concepts applied to Firehorse:
  • Agent autonomy: Each agent operates independently within defined responsibility areas
  • Agent communication: Agents exchange signals to coordinate dependencies
  • Emergent behavior: System-level capabilities arise from agent interactions
  • Coordination mechanisms: Protocols ensure agents work toward shared goals

    • 2.5.2 Lifetime Scope Signals Protocol

    The Lifetime Scope Signals protocol is a novel coordination mechanism developed for DWS IQ 6. It enables deterministic multi-agent development coordination. Unlike traditional MAS approaches based on real-time negotiation, this protocol uses declarative signal emission to unblock dependent agents. Signal format:

    2.5.3 MCP Hub Orchestration Patterns

    The Model Context Protocol (MCP) Hub (`mcp-hub/server.py`, port 8765) implements four workflow patterns for multi-agent coordination. Each pattern exposes a dedicated HTTP endpoint and handles agent routing, error propagation, and result aggregation. 1. Fan-Out Pattern (`POST /workflow/fan-out`) Distributes tasks to multiple agents in parallel using `asyncio.gather()`. All agents execute concurrently with a shared HTTP client (300s timeout). Exceptions are serialized per-task, enabling partial success — if one agent fails, others still return results. Used for Category B (Operations) agents where tasks are independent. 2. Sequential Pattern (`POST /workflow/sequential`) Executes tasks one by one in dependency order. Each task's result is injected as `context["previous_result"]` into the next task, creating an explicit data flow chain. Suitable for pipelines where output of one agent feeds the next (e.g., data extraction → analysis → report generation). 3. Reflection Pattern (`POST /workflow/reflection`) Implements an iterative implementation-evaluation loop. An implementation agent produces output, an evaluation agent scores it (0.0–1.0) and provides feedback. If the score falls below a configurable threshold (default 0.85), the feedback is injected back into the implementation agent for another iteration (max 3 by default). Used for Category C (Customer-facing) agents where output quality is critical. 4. Pipeline Pattern (`POST /workflow/pipeline`) — _Recommended for production_ Combines parallel and sequential execution through staged workflows. Each stage contains a list of tasks that execute in parallel (fan-out within stage), while stages execute sequentially (results from stage N flow as context into stage N+1). This avoids the sequential bottleneck while maintaining dependency ordering between logical phases. | Pattern | Parallelism | Context Passing | Best For | | ---------- | ---------------------- | --------------- | ----------------------- | | Fan-Out | Full parallel | None | Independent tasks | | Sequential | None | Previous → Next | Dependent chains | | Reflection | None | Feedback loop | Quality-critical output | | Pipeline | Parallel within stages | Stage → Stage | Production workloads |

  • Supply chain visibility across verticals. When a manufacturing customer reports CBAM imports, DWS IQ already understands the steel producer's ETS obligations, the logistics provider's fuel regulations, and the energy supplier's renewable certificates. This cross-industry knowledge means the customer's compliance reports are more accurate, audit-ready, and defensible because the platform understands every link in their value chain.
  • LWM cross-pollination. The Lifetime World Model learns from anonymized patterns across all 20 industries. A carbon reduction technique proven in cement manufacturing (e.g., clinker ratio optimization) generates transferable insight for construction (low-carbon concrete specification). The customer benefits from an LWM that has been trained on 20 industries' worth of climate intelligence — not just their own narrow domain.
  • Agent template reusability. Agent configurations that work in one industry accelerate deployment in related industries. The BIM compliance agent developed for construction is adapted for real estate energy performance certificates. The supply chain Scope 3 agent in manufacturing transfers to food & beverage. Customers in later-deploying industries get battle-tested agents at lower cost and faster deployment.
  • Regulatory early warning. When a new regulation (e.g., EU Deforestation Regulation) first impacts agriculture, the platform detects it and alerts food & beverage, textiles, and logistics customers proactively — before the regulation reaches their industry. A single-industry platform cannot provide this cross-sector foresight.
  • Benchmarking across peers and adjacent industries. An energy company can benchmark its emissions intensity not only against other utilities but against the industrial customers it serves (manufacturing, mining, chemicals). This multi-dimensional benchmarking gives the customer strategic insight into where they stand in the broader decarbonization landscape.
  • Network effects compound over time. Each new industry added to the platform makes every existing industry's LWM smarter. The 20th industry customer benefits from all 19 industries' accumulated intelligence. This creates a moat: a competitor starting with one industry must replicate years of cross-industry learning to match DWS IQ's accumulated intelligence.
    • The bottom line for the customer: DWS IQ's 16-industry coverage means their compliance intelligence is not isolated — it is connected to the entire EU industrial ecosystem. They pay for one platform and receive intelligence that would require 16 separate tools to approximate.

    • 10.10.7 Agent Memory Fact Extraction Pipeline (PR-254)

    _Session: claude/agent-memory-fact-extraction-gLEss | Date: 23.03.2026_ The EMPO² theoretical framework (Section 10.10.4) was operationalized through the Agent Memory Fact Extraction Pipeline — the first production implementation of the non-parametric memory update path. Architecture — Dual Memory Model: The system distinguishes two complementary memory layers: | Layer | Knowledge Type | Source | Example | | ------------------------------ | ---------------------- | ------------------------------------------------- | ---------------------------------- | | LWM (Lifetime World Model) | Domain knowledge | EU regulations, emission factors, industry models | "CBAM threshold is 150,000 EUR" | | Client Memory | Relationship knowledge | Conversations, emails, meetings | "ACME Corp prefers weekly reports" | LWM provides _what the agent knows about the world_; client memory provides _what the agent knows about this specific customer_. Conversation text
  → LLM extraction (Claude Haiku, structured prompt)
  → JSON array of {subject, predicate, value, confidence, category}
  → Confidence filter (≥0.7 threshold)
  → Duplicate detection (cosine similarity >0.95 in pgvector)
  → Persist as `fact` type in semantic_memories table
  → Available for recall via hybrid search (vector + text)

Three Missing Execution Layers: Fact extraction alone creates _passive knowledge_. Three additional layers are required to make this knowledge _actionable_:
  • Firehorse State Machine — The execution layer that acts on what memory + LWM know. Without it, the platform has knowledge but no action capability. Facts like "customer deadline is Q2 2026" need a state machine to trigger escalation workflows.
  • ERP Connector Layer — The real-world data feed. Memory and LWM are only as good as the live data flowing from Visma/IFS/SAP. Client memory captures _stated_ preferences; ERP data reveals _actual_ behavior (order patterns, payment history, usage metrics).
  • KYA Governance Wrapper — The trust layer. Client memory + LWM without attestation is a chatbot. KYA (Know Your AI, internal v1.4 / public v1.1) wraps every memory decision with audit-grade provenance: "fact A replaced fact B at timestamp X, approved by agent Y, logged to Firehorse." This is essential for EU compliance audits under CSRD and EU AI Act Article 12.

    • 10.13 Claude Code Engineering Structure: AI Workflow as First-Class Engineering

    10.13.1 Motivation

    As Claude Code adoption scales beyond individual experiments, a decisive architectural split emerges: projects treating AI workflows as temporary chat interactions diverge sharply from those engineering them as first-class software components. The DWS6 repository embodies the latter approach, and this section documents the principles that make it work at enterprise scale. The core insight — validated by emerging Claude Code community practice in 2026 — is that the same separation of concerns used in software engineering applies equally to AI workflow design. A prompt is not a product; a skill is.

    10.13.2 CLAUDE.md as Project Memory

    Traditional AI usage repeats context in every prompt, creating two compounding costs: token waste and behavioral drift.     10.13.4 Hooks for Automated Workflow Validation

    Hooks are the enforcement layer of AI workflow engineering — and the most underutilized pattern in current practice. Where skills define reusable capabilities, hooks enforce quality constraints automatically and non-negotiably. DWS6 implements hooks at two levels: Claude Code hooks (`.claude/hooks/`):
  • Tool output transformation — normalize agent JSON responses to consistent schema
  • Structured output verification — ensure all CLI commands produce valid JSON
  • Session start validation — verify environment readiness before agent work begins
    • Git hooks (`.githooks/`):
  • Branch name enforcement — `claude/-` naming convention before commit
  • Pre-commit security checks — detect hardcoded secrets, unsafe exec() patterns
    • The critical property of hooks is non-negotiability: unlike CLAUDE.md guidance (which an agent may follow imperfectly), hooks intercept tool calls and either transform or block them. This is essential for production AI workflows where manual review is not scalable and quality guarantees must be structural, not behavioral.

    • 10.17 Conclusion: The Carbon Balance Sheet as Compliance Infrastructure

    10.17.1 From Reporting to Reconciliation

    The central finding of this thesis is that EU climate compliance across ETS, CBAM, CSRD, and the EU Taxonomy is not a reporting problem — it is a ledger problem. The same tonne of CO2e that appears as an ETS surrender debit for a steel mill becomes a CBAM embedded emission for the importer, becomes a CSRD Scope 3 upstream disclosure for the construction company, and determines their Taxonomy alignment. Four regulatory touchpoints, one physical quantity. Current compliance tools treat each regulation as an independent reporting workflow. This produces duplicated data entry, inconsistent emission factors, and no reconciliation between related obligations. The result: enterprises report the same carbon event differently across regulations, auditors cannot cross-verify, and Scope 3 estimates carry ±40% uncertainty because they rely on spend-based proxies rather than transaction-verified data.

    10.17.2 Double-Entry Bookkeeping for CO2

    This thesis proposes that carbon compliance requires the same architectural solution that financial accounting adopted centuries ago: double-entry bookkeeping. Every compliance event produces a journal entry — debit or credit — in dual units (EUR and tCO2e): | Compliance Event | Debit (liability) | Credit (asset) | Regulation | | ---------------------------------- | ------------------------- | ---------------------------------- | -------------------- | | ETS allowance surrender | tCO2e emitted + EUR cost | — | EU ETS | | Free allocation received | — | tCO2e allocated | EU ETS | | CBAM certificate purchase | EUR paid + tCO2e imported | — | CBAM | | CBAM origin carbon price deduction | — | EUR already paid in origin country | CBAM | | Verified offset retirement | — | tCO2e offset | Voluntary / Taxonomy | The carbon balance sheet — total liabilities (debits) minus total assets (credits) — gives a CFO a net carbon position that is auditable, reconcilable, and machine-readable (XBRL/iXBRL).

    10.17.3 Cross-Regulation Reconciliation

    The debit-credit ledger enables what no current tool provides: cross-regulation reconciliation. When a steel mill's ETS data and a construction company's CBAM data flow through the same ledger, the system can verify that embedded emissions match actual production emissions. This eliminates the reliance on CBAM default values (which overestimate by 20-50%) and produces transaction-verified Scope 3 data with ±3% accuracy instead of the ±40% from spend-based estimation. This is also a network effect: when Customer A's verified emissions improve Customer B's CBAM factor accuracy, both benefit. The more industries on the ledger, the more cross-vertical intelligence emerges.
