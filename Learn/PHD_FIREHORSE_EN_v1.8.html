Abstract

This thesis documents the implementation of the Firehorse Operations Model, an AI-assisted approach to e-commerce store management using Claude Code. The model demonstrates significant efficiency gains in product catalog management, Google Merchant Center integration, and payment processing through Revolut Business. We present the technical architecture, operational workflows, and future evolution toward audio-based customer interactions with industry-specific carbon calculator integration and EU regulatory compliance. Keywords: AI Operations, E-Commerce Automation, Google Merchant Center, Claude Code, Firehorse Model, EU AI Act Compliance, Carbon Calculator, Industrial Compliance

    • 1. Introduction

    1.1 Background

    The enterprise software market increasingly demands rapid product iteration, compliance with EU regulations, and seamless customer experiences. Traditional e-commerce operations require manual intervention for product updates, feed management, and customer support. The Firehorse Operations Model addresses these challenges through AI-native automation using Claude Code. Lifetime Oy operates DWS10.com, an enterprise e-commerce platform serving climate intelligence solutions, compliance software, and professional consulting services to 16 EU-regulated industries. The platform integrates with:
  • Google Merchant Center (Account ID: 8496329) for product visibility
  • Revolut Business for checkout and payment processing
  • Claude Code for automated store maintenance via Firehorse operations model
  • Cloudflare Pages for static hosting with EU data residency

    4.3 Feed Generation Pipeline

    javascript
// generate-feed.cjs workflow
const generateFeed = () => {
  // 1. Load products.json
  const products = require('../config/products.json');

  // 2. Validate required fields
  validateProducts(products); // id, mpn, price, brand

  // 3. Generate XML with g: namespace
  let xml = generateXMLHeader();

  for (const product of products) {
    xml += generateProductItem(product);

    // 4. Add checkout_link_template for Revolut
    const checkoutLink = product.revolutLink || 'https://revolut.me/lifetimeoy';
    xml += `<g:checkout_link_template>${checkoutLink}</g:checkout_link_template>`;
  }

  // 5. Write google-products.xml
  writeFile('google-products.xml', xml);
};

    7. EU Regulatory Compliance

    7.1 EU AI Act Requirements (August 2026)

    The EU AI Act classifies AI systems by risk level. Our audio chat and recommendation system falls under Limited Risk category, requiring:
  • Transparency: Inform users they're interacting with AI
  • Human oversight: Escalation path to human support
  • Documentation: System capabilities and limitations
  • Data protection: GDPR-compliant data handling
  • Reasoning lineage: Traceable decision chains

    • 13. Prompt Caching Architecture for AI Agents

    13.1 Engineering Principle: Cache Rules Everything

    The Firehorse Operations Model relies on long-running AI agent sessions (Claude Code) for store management, product updates, and compliance automation. Prompt caching is the foundational engineering principle that makes these sessions economically viable. Source: Thariq Shihipar (Anthropic), "Lessons from Building Claude Code: Prompt Caching Is Everything" (2026). Core insight: Prompt caching reuses computation from previous API roundtrips via prefix matching. The API caches everything from the start of the request up to each `cache_control` breakpoint. A high cache hit rate reduces costs and latency significantly.

    13.2 System Prompt Layout for Caching

    The order of prompt content matters — static content first, dynamic content last: 
    
1. Static system prompt & Tools     (globally cached)
2. CLAUDE.md / project config       (cached within a project)
3. Session context                   (cached within a session)
4. Conversation messages             (new per turn)
    Fragility warning: Cache ordering breaks when:
  • Timestamps are placed in the static system prompt
  • Tool definitions are shuffled non-deterministically
  • Tool parameters are updated mid-session (e.g., available agents)

    • 13.3 Six Engineering Rules for Agent Caching

    | Rule | Principle | Implementation | |------|-----------|---------------| | 1. Static first, dynamic last | Maximize shared prefix across sessions | System prompt → CLAUDE.md → session context → messages | | 2. Use system messages for updates | Never modify the static prompt mid-session | Pass time, file changes, mode switches via `` tags in the next message | | 3. Never change models mid-session | Prompt caches are model-specific | Switching from Opus to Haiku at 100k tokens costs more than keeping Opus (cache rebuild) | | 4. Never add/remove tools mid-session | Tools are part of the cached prefix | Use tool stubs with `defer_loading: true` for optional tools; discover via ToolSearch | | 5. Design features around the cache | State transitions via tools, not tool set changes | Plan mode = system message + ExitPlanMode tool, not swapping the tool set | | 6. Fork operations share parent prefix | Compaction/summarization must reuse cache | Use identical system prompt, tools, and message history for forked requests |

    13.4 Compaction: Cache-Safe Context Forking

    When running agents approach the context window limit, compaction (summarization) must preserve the cache: 
    
WRONG: New API call with different system prompt + no tools
       → Full cache miss, expensive

RIGHT: Same system prompt + same tools + parent message history
       + compaction prompt appended as new user message
       → Cache hit on parent prefix, only new tokens are the prompt
    This requires reserving a "compaction buffer" — enough room in the context window for the compact message and summary output tokens.

    13.5 Operational Impact on Firehorse

    For DWS10.com store operations, these caching principles translate to: | Operation | Cache Impact | Practice | |-----------|-------------|----------| | Product catalog updates | Long session, many file edits | Keep same model throughout | | Feed generation | Tool-heavy workflow | All tools defined at session start | | Compliance checking | Context-heavy (regulations) | CLAUDE.md cached as project config | | Multi-file sync (dual folder) | Sequential dependent operations | Chain in single session, don't fork | Monitoring: Cache hit rate is treated as an uptime metric. A drop in cache hits triggers investigation — it indicates a system prompt change, tool definition shift, or model switch that needs correction.

    13.6 Cost & Latency Implications

    | Scenario | Cache Hit Rate | Relative Cost | Latency | |----------|---------------|---------------|---------| | Optimized (static prefix) | >90% | 1x (baseline) | Low | | Tool set changes mid-session | ~50% | ~2x | High | | Model switch mid-session | 0% (full rebuild) | ~3-5x | Very high | | Compaction without parent prefix | 0% | ~3x | High | These economics are critical for Firehorse's AI-assisted store operations, where sessions routinely process 30+ products across multiple files.

    14.6.3 Lifetime Scope Signals for LWM Training Coordination

    Session: claude/pedantic-easley | Date: 07.03.2026 The Lifetime Scope Signals (LSS) protocol — originally designed for deterministic multi-agent development coordination (see Metropolia thesis Section 2.5.2) — extends naturally to ML pipeline orchestration. Rather than introducing a dedicated ML workflow engine (Kubeflow, Airflow), the LWM training pipeline is coordinated using the same four signal types: READY, COMPLETE, ERROR, BLOCKED. Training Agent Fleet (T-01 through T-10): | Agent ID | Name | Role | Emits | Listens For | |----------|------|------|-------|-------------| | T-01 | InfraVerifier | Validate CUDA/PyTorch on GN-100 nodes | `COMPLETE:infra-verified` | (none — entry point) | | T-02 | ModelFetcher | Download base model to shared storage | `READY:base-model` | `T-01:COMPLETE:infra-verified` | | T-03 | CurriculumAgent | Claude API curriculum design per vertical | `READY:curriculum:{vertical}` | `T-02:READY:base-model` | | T-04 | DataSynthAgent | Generate 2000+ synthetic examples | `READY:dataset:{vertical}` | `T-03:READY:curriculum:{vertical}` | | T-05 | TrainingAgent | QLoRA fine-tuning on assigned node | `READY:lora-weights:{vertical}` | `T-04:READY:dataset:{vertical}`, `T-06:READY:node-slot` | | T-06 | ResourceArbiter | Allocate GN-100 node slots (2 tokens) | `READY:node-slot` | `T-05:READY:lora-weights:` (releases slot) | | T-07 | EvalAgent | Claude-as-judge, quality gate ≥7.0 | `READY:eval-pass:{vertical}` / `ERROR:eval-fail:{vertical}` | `T-05:READY:lora-weights:{vertical}` | | T-08 | MergeAgent | Merge LoRA adapter into base model | `READY:merged-model:{vertical}` | `T-07:READY:eval-pass:{vertical}` | | T-09 | DeployAgent | Deploy inference API | `COMPLETE:lwm-deployed:{vertical}` | `T-08:READY:merged-model:{vertical}` | | T-10 | PipelineOrchestrator | Monitor all verticals | `COMPLETE:lwm-all-verticals` | All `T-09:COMPLETE:` | The `{vertical}` parameterized milestone enables per-industry pipeline instantiation — the only protocol extension over base LSS v1.0. Key mechanisms:
  • Quality gate signals — T-07 emits `READY:eval-pass:{vertical}` only when Claude-as-judge score ≥7.0; failure emits `ERROR:eval-fail:{vertical}`, triggering curriculum re-generation (max 3 retries → `BLOCKED` → human escalation). This maps to the EMPO² off-policy update pattern (Section 14.6.2).
  • Resource arbitration — T-06 manages two node-slot tokens (one per GN-100). Training agents acquire a token before starting; release on completion. First-come-first-served by signal emission order.
  • Fan-Out parallelism — Curriculum generation (T-03) and data synthesis (T-04) run across all 16 verticals simultaneously (CPU-bound, no GPU constraint), eliminating idle GPU time.
    • Firehorse operating model impact: The training coordination validates LSS as a general-purpose deterministic coordination mechanism — the same protocol orchestrates both software development agents (Appendix F) and ML training pipelines, reducing operational complexity for Firehorse customers who need both capabilities.

    Appendix F: Claude Code Engineering Structure — AI Workflow as First-Class Engineering

    The Firehorse operations model is built on a principle that emerges from both the research findings and operational practice: AI workflows must be engineered, not improvised. This appendix documents the concrete structural patterns that implement this principle in the DWS6 repository, validated against emerging Claude Code community best practices (2026). CLAUDE.md as Project Memory The `CLAUDE.md` file at the repository root is not documentation — it is the primary intelligence substrate for every AI agent session. It encodes standards, constraints, architecture decisions, email rules, security controls, and non-negotiables in a single file that every Claude Code session reads automatically. This eliminates behavioral drift and removes the need for repeated per-session context injection. Key metric: 2,000+ lines of institutional knowledge (brand standards, document standards, security controls, deployment rules, thesis rules, email rules) inherited by every session at zero marginal cost. Skills as Reusable Workflow Components Six production skills in `.claude/commands/` transform ad-hoc prompting into callable, documented, testable workflow components: | Skill | Domain | |-------|--------| | `/compliance-check` | EU ETS/CBAM/CSRD regulatory gap analysis | | `/agent-run` | Execute any DWS IQ agent via structured CLI | | `/workflow` | Chain multiple agents into unified reports | | `/discover-agents` | Agent capability discovery | | `/site-safety` | Construction site safety (EN 13001) | | `/carbon-analysis` | Embodied carbon lifecycle assessment | Each skill is an engineered component with a defined interface, documentation, and failure modes. This is the Build for Agents principle in practice. Hooks for Automated Quality Enforcement Git hooks (`.githooks/`) enforce structural invariants:
  • Branch naming convention (`claude/-`) — prevents incorrect branch workflows
  • Anti-destructive-push guard — prevents accidental deletion of production branches
  • Post-merge sync — keeps Admin/, docs/, AgentFoundry/ synchronized to backup storage
    • The quality enforcement is structural, not behavioral — hooks cannot be bypassed by agent behavior. This is the key architectural distinction between a disciplined AI workflow system and an ad-hoc one. Subagents for Context Isolation and Parallel Execution Background agents enable parallel research and task execution without exhausting the main context window. The Explore agent specifically provides codebase search without polluting the primary context — critical for large repositories. This pattern directly extends the multi-agent orchestration documented in Sections 3 and 14. Conclusion The architectural lesson for the Firehorse Operations Model: the difference between AI experiments and AI products is not the model — it is the engineering discipline applied to how the model is integrated. CLAUDE.md, skills, hooks, and subagents are not features; they are the infrastructure that makes the Firehorse model reliable, consistent, and scalable.
